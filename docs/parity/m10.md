# M10: Hardening and final parity audit, implementation spec

**Base branch:** `parity/m10-hardening`, cut from `main` at `53353d8` (M0–M9 merged, #16–#27). Migrations exist up to **031** (030–031 M9). M10 adds **032** (drops the legacy `integration_endpoints` table, see Step 0) and nothing else.

**Shape:**
- **Step 0** (orchestrator) commits the dependencies, migration 032, the frozen contracts (logger API, health route stubs, npm script entries, the final `ci.yml` job layout, the `.env.example` block), and updates the route-coverage test. The build stays green; behaviour is unchanged.
- **Four parallel packages, A–D,** with strictly disjoint file ownership:
  - **A:** browser e2e in CI. Service containers, the worker in CI, fake ASR, structured LLM replay, the core-flow and bot specs, CI artifacts.
  - **B:** observability (pino, optional Sentry, request ids), health and readiness for the app and the worker, the Redis rate limiter, and deploy (deploy.yml ↔ `deploy-vps.sh`, rollback, digest-pinned images, runbooks, env matrix).
  - **C:** the bundle diet for `/[locale]` and `/share/[token]`, and the design-system leftovers, so that `ds:check --strict` and `bundle:check --strict` pass.
  - **D:** truthful docs (README, SETUP, API reference, runbook index), the generated `db/schema.sql` plus its CI check, the non-ops remaining-risk fixes, and the final parity audit (`docs/parity/AUDIT.md`).
- The **Integration step** flips `ds:check` and `bundle:check` to `--strict` in CI, pins GitHub Actions by SHA, requires the e2e and schema jobs, and records the audit evidence in STATUS.

**Goal:** close the programme. Every parity-matrix row is ✓ with evidence a reviewer can rerun without keys. The Hebrew rows are demonstrably better than Fireflies wherever that can be measured offline. Whatever still needs the user's keys or accounts is listed, with a ready harness and a one-command live run.

**Non-goals:** production deploys (`DEPLOY_ENABLED` stays unset), new product features, live runs that need credentials we don't have.

## Decisions (normative)
### E2E in CI
- **A separate workflow, `.github/workflows/e2e.yml`**, runs on `pull_request` and `push` to `main`, needs **no secrets**, and uses a **matrix of five jobs**, each with its own empty database: `core`, `m6`, `m8`, `m9`, `m9-prod`.
  - Why a matrix: the seeds collide, `E2E_ENV_FILE` is global, and parallel jobs finish faster than sequential reseeding.
- **Services per job:**
  - `postgres: pgvector/pgvector:0.8.1-pg17@sha256:<digest>` (the same digest B pins in compose), with a health option `pg_isready`;
  - `redis: redis:<7.4.x>-alpine@sha256:<digest>`, with a health option `redis-cli ping`;
  - **MinIO started by a `docker run -d` step** (same digest as compose, `server /data`), because GitHub service containers can't pass a `command`. Then `mc mb` (or the app's bucket bootstrap) creates `S3_BUCKET`.
- **Per-run secrets:** `scripts/e2e/ci-env.sh` writes `.env.e2e` with values from `openssl rand -hex 32` (session, webhook and token-encryption keys) and fixed loopback URLs. These are test values for a throwaway run. They are never echoed, and `.env.e2e` and `.secrets/` are never uploaded.
- **Order per job:**
  1. `npm ci` (cached), plus `npx playwright install --with-deps chromium` (cached by Playwright version);
  2. `sudo apt-get install -y ffmpeg poppler-utils` (media prepare; the m9 `pdftotext` step);
  3. `npm run db:migrate`, then the suite's seed (`search:e2e-seed`, `integrations:e2e-seed`, `m9:e2e-seed` or the new `m10:e2e-seed`);
  4. start the fake server (`npm run integrations:fake`, which also serves fake ASR, see below);
  5. start the worker (`npm run worker`, with `MEETSUM_WORKER_HEALTH_PORT`) and wait for B's `/ready`; until B lands, wait for the BullMQ `ready` log line;
  6. start the app (`next dev` for the functional suites; `next build && next start` for `m9-prod`);
  7. warm up: GET each route the suite visits until it answers 200 (dev compiles on demand), with a 180 s cap;
  8. `npx playwright test <suite>`;
  9. always upload the artifacts, then dump the app, worker and fake-server logs (they are scrubbed, see B) into the artifact.
- **`m9-prod`** runs only the steps that need a production build: SW registration and the cache contents (17.11), production error pages (no `error.message`), and the manifest. It uses **no fakes and no replay** (they are refused in production), with non-placeholder per-run secrets. It never gets a production bypass flag: no `MEETSUM_ALLOW_*` is added for tests.
- **Artifacts** (`actions/upload-artifact`, `if: always()`, 14-day retention, never committed): `test-results/**` (screenshots, `a11y-report.json`, `index.md`, traces), `playwright-report/**` and `e2e-logs/**`.
  - Traces carry the seeded test users' cookies. These are per-run random values for a database that is thrown away, which is acceptable. Real credentials never enter a job.
- **Required checks:** all five jobs become required at the Integration step. While A is in progress the workflow runs, but failures don't block other PRs.
- `playwright.config.ts` gains `outputDir: "test-results"`, the reporters `[["list"],["html",{open:"never"}],["json",{outputFile:"test-results/results.json"}]]`, a `projects` entry per suite (`core`, `m6`, `m8`, `m9`, `m9-prod`) with its own `testMatch`, `retries: process.env.CI ? 1 : 0`, `screenshot: "only-on-failure"` and `video: "retain-on-failure"`. Still **no `webServer`**: the workflow and the operator start the servers, and local runs stay as documented.

### Fake ASR and structured replay (no keys, non-production only)
- **Fake ASR** (`lib/testing/fake-asr.ts`, registered in the fake server): `GET /asr/v1/models` and `POST /asr/v1/audio/transcriptions` return a **fixture chosen by the uploaded file's SHA-256** (`tests/fixtures/e2e/asr/<sha256>.json`). The fixture is a `verbose_json` response with code-switched Hebrew/English segments and word timestamps. An unknown hash returns 422 so a wrong fixture fails loudly. The core job sets `LOCAL_TRANSCRIPTION_URL=http://127.0.0.1:4010/asr` and `MEETSUM_ASR_CHAIN=local-whisper`.
- **Audio fixture:** `tests/fixtures/e2e/media/he-en-30s.wav`, generated once and committed by `scripts/e2e/make-audio-fixture.ts`. It is a 30 s, 16 kHz mono tone sequence, under 1 MB, deterministic, and contains no voice, so it raises no consent issue. The ASR fixture supplies the "speech".
- **Structured LLM replay:** `MEETSUM_LLM_REPLAY_DIR` (already the Ask switch, still refused when `NODE_ENV=production`) also serves the non-streaming structured calls.
  - The key is `<task>/<fixtureId>.json`, where `task` is the router task (title, tags, summary, chapters, …) and `fixtureId` is the ASR fixture id carried in the meeting's transcript metadata. It is **not** a prompt hash, so prompt edits don't break e2e.
  - Responses go through the same zod validation and citation check as live output, so a bad fixture fails like a bad model would.
  - Fixtures cite segments by the ordinal ids the prompt presents.
  - A missing replay file is a hard error when the replay directory is set. It never silently falls back to the heuristic path.
- Replay and fake ASR are listed in AUDIT as "pipeline wiring evidence, not quality evidence". Quality evidence comes only from the eval tables.

### Observability
- **pino** is the only server logger: `lib/log/index.ts` exports `logger`, `getLogger(bindings)`, `withLogContext(bindings, fn)` (AsyncLocalStorage) and `scrub(value)`.
  - Output is JSON to stdout, with no transports (they use worker threads, which Next bundling breaks). `pino` is in `serverExternalPackages`.
  - `LOG_LEVEL` defaults to `info` in production and `debug` otherwise. `pino-pretty` is a developer pipe, not a dependency.
  - Every line carries `service` (`app` | `worker` | `migrate`), `version` (from `package.json`, never `npm_package_version`), and the context bindings.
- **Redaction**, in two layers:
  - pino `redact.paths` (censor `"[redacted]"`): `req.headers.authorization`, `req.headers.cookie`, `res.headers["set-cookie"]`, `*.token`, `*.accessToken`, `*.refreshToken`, `*.idToken`, `*.password`, `*.passwordHash`, `*.secret`, `*.clientSecret`, `*.apiKey`, `*.passcode`, `*.code`, `*.codeVerifier`, `*.authorization`, `*.cookie`;
  - a `formatters.log` deep scrub (depth 4) that redacts keys matching `/token|secret|password|passcode|authori[sz]ation|cookie|api[-_]?key|verifier|signature/i` at any level, masks email values (`d***@example.com`), strips query strings from URL-shaped values, and runs the existing `redactBotText`, `redactIntegrationError` and `redactAsrErrorMessage` on `err.message` and `err.stack`;
  - transcript, summary, question and comment text are never logged; there is a test with a seeded canary.
  - `botLog` and `integrationLog` become thin wrappers over `getLogger({ component })`, keeping their call sites.
- **Request ids:**
  - `proxy.ts` accepts an incoming `x-request-id` matching `^[A-Za-z0-9._-]{8,64}$`, otherwise generates a UUID. It forwards the id on the request and echoes it on the response.
  - `withAuthz`/`withPublicRoute` wrap each handler in `withLogContext({ reqId, route, method, workspaceId?, principal: "session"|"api_key"|"public" })`.
  - Worker jobs run in `withLogContext({ jobId, queue, jobName, workspaceId? })`.
  - Error responses already carry codes; they gain no extra fields.
- **`no-console`** (`error`) covers `lib/**`, `app/**`, `worker/**`, `instrumentation.ts` and `proxy.ts`. `scripts/**`, `mcp/**`, `desktop-recorder/**` and tests are exempt. Client components keep 0 (already true).
- **Sentry:**
  - It is **optional, server and worker only, and off when `SENTRY_DSN` is unset**: the module is then never imported (dynamic import in `instrumentation.ts` `register()` and in `worker/index.ts`).
  - `@sentry/node`, with `sendDefaultPii: false` and `tracesSampleRate` from `SENTRY_TRACES_SAMPLE_RATE` (default 0).
  - `beforeSend` and `beforeBreadcrumb` drop request cookies, headers, body and query, drop `user.email`/`ip_address`, and run `scrub()` on messages, exception values, extra and contexts. Breadcrumb URLs lose their query.
  - `environment` comes from `SENTRY_ENVIRONMENT`; `release` is the package version plus the git SHA (`MEETSUM_GIT_SHA`, a build arg).
  - `instrumentation.ts` exports `onRequestError` (forwards to Sentry when it's enabled; always logs through pino).
  - GlitchTip (self-hosted, Sentry-compatible) works with the same DSN variable. The runbook says so.
  - **No client SDK** (bundle budget, PII). OpenTelemetry export is not added; the AUDIT lists it as a follow-up.
- **Health:**
  - `GET /api/health/live`: 200 `{status:"ok"}`, no dependency calls.
  - `GET /api/health/ready`: 200, or 503 with `{status, checks:{database, redis, storage, migrations}}`, each check `"ok"|"fail"|"skip"`. The checks:
    - DB `select 1` (2 s);
    - Redis `PING` (1 s, `skip` when `REDIS_URL` is unset outside production);
    - S3 `HeadBucket` (2 s);
    - migrations: the highest file version equals the highest row in `schema_migrations`.
  - The ready response never carries error text, hosts or tenant data.
  - Both routes are public, listed in the route-coverage public allowlist, and rate-limited per IP like other public routes.
  - `/api/health` keeps its shape for compatibility, with a real Redis ping, a storage check and the correct `version`.
- **Worker health:** an HTTP server on `MEETSUM_WORKER_HEALTH_PORT` (default 3101; bind `MEETSUM_WORKER_HEALTH_HOST`, default `0.0.0.0` inside the container, never published).
  - `/live` checks the event loop (a lag under 2 s).
  - `/ready` checks Redis `PING`, DB `select 1`, and that every started BullMQ worker reports `isRunning()`.
  - SIGTERM drains (`worker.close()`) and closes the server.

### Rate limiter (R1)
- `lib/rate-limit.ts` becomes async: `checkRateLimit(key, config): Promise<RateLimitResult>`, `checkRateLimitWindows`, `rateLimitRequest`. The backend is chosen by `MEETSUM_RATE_LIMIT_BACKEND=memory|redis`. The default is `redis` when `REDIS_URL` is set, otherwise `memory`.
- **Redis algorithm:** a sliding window in one Lua script over a sorted set (`ZREMRANGEBYSCORE` + `ZCARD` + `ZADD` + `PEXPIRE`). Keys are `rl:<preset>:<sha256(key)>`; raw IPs and user ids are never stored in Redis keys. A dedicated ioredis connection comes from the existing BullMQ connection options.
- **Redis failure:**
  - **Fail closed** for the presets that guard abuse or cost: `share-verify`, `ask`, `llmOnDemand`, `auth`, `exports`, `search`.
  - **Fall back to the per-instance memory limiter** for everything else, logged once per minute.
  - The preset table gains a `failClosed` flag. It is an open question for the user (see the end).
- `MEETSUM_RATE_LIMIT_ENABLED=false` (the existing switch) still disables limiting.

### Deploy
- **One deploy path:** `deploy.yml` runs `./scripts/deploy-vps.sh` over SSH. Nothing else is inlined. The gate stays `github.ref == 'refs/heads/main' && vars.DEPLOY_ENABLED == 'true'`, plus `environment: production` (reviewers configurable by the user). The quality gate calls the CI workflow as a reusable workflow (`workflow_call`), so it is Node 24 with lint, test, build, ds and bundle.
- **One image per deploy:** compose `app`, `worker` and `migrate` share `image: meetsum:${MEETSUM_IMAGE_TAG}` with `build:` only on `app`, so one build serves all three. `deploy-vps.sh`:
  1. `flock /opt/meetsum/.deploy.lock` serializes manual and CI deploys;
  2. preflight: the env file exists, `docker compose config -q`, at least 5 GB disk free;
  3. backup (hard fail);
  4. record `PREV_SHA` and `PREV_TAG` and `git pull --ff-only`;
  5. `docker compose build app` (one `next build`), tag `meetsum:<sha>` and keep `meetsum:previous`;
  6. **migrations before the switch:** `run --rm migrate` with the new image. This is forward-only and must be backward-compatible with the previous release (expand/contract policy in the runbook);
  7. `up -d --no-deps app worker`;
  8. readiness: poll `docker compose exec -T app wget -qO- http://127.0.0.1:3000/api/health/ready` and the worker `/ready` for up to 120 s;
  9. on failure, **automatic rollback** of code and image: retag `meetsum:previous`, `git checkout $PREV_SHA`, `up -d --no-deps app worker`, wait for ready, exit non-zero. The database is **not** rolled back automatically: restoring the pre-deploy backup is a manual, documented step (`scripts/restore-postgres.sh`).
- `scripts/rollback-vps.sh [<sha>]` is the manual equivalent of step 9.
- **Pin every image by tag and digest** in every compose file and the Dockerfile (`node:24.x-alpine@sha256:…`, pgvector, redis, minio, n8n, faster-whisper, plus the existing Vexa pins). Digests are resolved at implementation time with `docker buildx imagetools inspect` and recorded with the date. `tests/image-pins.test.ts` fails on any `image:`/`FROM` without `@sha256:` or with `latest`. `.github/dependabot.yml` proposes bumps for `docker` and `github-actions` weekly (needs no secrets).

### Schema (D)
- **`db/schema.sql` becomes generated:** migrations 001–032 are applied to an empty `pgvector/pgvector:0.8.1-pg17` database (with the vector extension available), then dumped with `pg_dump --schema-only --no-owner --no-privileges --no-comments --quote-all-identifiers=false`. The normalizer (`lib/db/schema-dump.ts`, pure, unit-tested) then:
  - drops the `\restrict`/`\unrestrict` lines (PG 17.6+), the `SET …` and `SELECT pg_catalog.set_config(…)` lines and the `-- Dumped from/by` headers;
  - collapses blank runs and normalizes to LF;
  - prepends a header: `-- GENERATED by npm run db:schema:generate from db/migrations (001–032). Do not edit.`

  Data and `schema_migrations` rows are excluded; its DDL stays.
- `npm run db:schema:generate` writes the file, and `npm run db:schema:check` diffs and prints a unified diff. `PG_DUMP_CMD` overrides the dump command; in CI it is `docker exec <service id> pg_dump`, so the client version always matches server 17.
- **CI job `schema`** (in `ci.yml`, Step 0 lays it out) uses a pgvector service container and runs `npm ci`, then `npm run db:schema:check` against `postgresql://…/schema_check`.
- The eleven "is mirrored in db/schema.sql" assertions are **deleted**: the CI diff replaces them. The migration-content assertions in those tests stay.
- A second check in the same job applies the migrations **twice** (`npm run db:migrate` re-run, which must be a no-op) and once on plain `postgres:17` without pgvector (the lexical-path NOTICE; the dump differs only by the vector objects). This proves idempotency and the guarded vector path.

### Integration: 404 document (2026-10-14)
Checked with `next dev` and with `next start` on the integration build: every `notFound()` response (the `[...rest]` catch-all, `invite/accept`, and so on) is sent with status 404 as Next 16.2's `<html id="__next_error__">` shell, **without** `lang`/`dir`, in production as well as in dev. Next's SSR catches the not-found error at the top level (`app-render.js`, `getErrorRSCPayload`) and the client renders the `[locale]` layout and `not-found.tsx` from the RSC payload, which carries `lang`/`dir`. After hydration the document is `<html lang="he" dir="rtl">` (or `en`/`ltr`) and the localized "page not found" view, verified in a browser for both locales. A `Suspense` boundary around the catch-all gives a server-rendered `lang` but turns the status into 200, so it was rejected. Tests: `m9-prod` asserts 404 plus `lang`/`dir` and no `__next_error__` id on the hydrated document, and the `404` screenshot surface waits for `html[lang][dir]` before axe runs. The remaining gap (no `lang` in the server HTML of 404 responses, so non-JS clients see an unlabelled error shell) is a framework limitation and is listed in AUDIT's follow-ups.
