# M7 — Meeting bot (Vexa sidecar): implementation spec

The base branch is `parity/m7-bot`, stacked on `parity/m6-search`. It assumes M2–M6 are integrated:
- M2: `withAuthz`, `ctx.meetings`, `getSystemMeetingRepository`, `workspace_settings`, `meetingScopeSql`, and jobs that carry `workspaceId`.
- M3: `transcribeWithRouter`, speaker suggestions with the `MeetTimelineEntry` loader.
- M4: `media_assets.kind`, `media.prepare`, the player, and `lib/client/polling.ts` `nextPollDelay`.
- M5 and M6: `lib/i18n/mN/*` merged by `dictionaries.ts`, and the SSE helpers.

Migrations exist up to 023; this spec adds **024**. There are three parallel packages, A/B/C, with strictly disjoint file ownership. The orchestrator commits Step 0 first. No Vexa instance is needed to build or test: every network path takes an injected `fetch`, and the fixtures are built from the documented shapes.

## Vexa facts (verified 2026-10-13 against docs.vexa.ai, the repo README and the GitHub releases API)

**Pinned version.** Pin **`v0.12.28`** (2026-10-09), the latest stable release. `v0.13.1` is an alpha and is not used. Compose deployments in 0.12.28 default to the versitygw object store, and `MINIO_ENDPOINT` is the storage setting. `v0.12.27` stopped returning the webhook secret in clear text, so any older secret must be rotated.

**Bots API.** All calls use the `X-API-Key` header.
- `POST /bots` takes `{platform: google_meet|teams|zoom, native_meeting_id, bot_name, language?, task?, transcribe_enabled?, recording_enabled?, passcode?, meeting_url?, teams_base_host?, authenticated?, automatic_leave:{max_time_left_alone (ms)}}`.
  - An explicit `native_meeting_id` overrides the URL.
  - A passcode in the URL wins over the `passcode` field.
  - Error codes:
    - 403 means the concurrency limit was hit (429 is the intended code but not what it returns today).
    - 409 means a bot is already in that meeting.
    - 422 means a bad link or field. Alias fields such as `password` are rejected.
    - 503 means transcription is enabled but no STT backend is configured. **We always send `transcribe_enabled:false` unless the live flag is on**, because our own ASR router produces the final transcript.
    - `auth_session_missing` is returned when `authenticated:true` and the bot's browser profile is signed out.
  - **The response body is not documented**, so parse it tolerantly.
- `DELETE /bots/{platform}/{native_meeting_id}` returns `{"status":"stopping","meeting_id",…}`.
- `GET /bots/status` returns `running_bots` (the 0.10 shape) plus `running`/`count` (the 0.12 shape).

**Meetings API.**
- `GET /meetings/{id}` returns `{id, platform, native_meeting_id, status, start_time, end_time, constructed_meeting_url, recordings, data:{service_provenance?}}`.
- Status values:
  - Planned: `idle` and `scheduled`.
  - Live: `requested`, `joining`, `awaiting_admission`, `needs_help`, `active` and `stopping`.
  - Terminal: `completed` and `failed`.
- `DELETE /meetings/{id}` (on a terminal meeting) erases the transcript and the recording objects. It returns 409 while the bot is in the meeting.

**Recordings and transcripts.**
- Recordings are **audio only**.
- `GET /recordings/{rid}/master?type=audio` returns `raw_url`.
- `GET /recordings/{rid}/media/{mid}/raw` is a byte stream with Range support.
- `GET /transcripts/by-id/{id}` returns `segments[{segment_id, speaker, text, start, end (seconds), language, completed, confidence, words[]}]`.

**Webhooks.**
- Configured with `PUT /user/webhook {webhook_url, webhook_secret, webhook_events:{name:bool}}`.
- Events: `meeting.status_change`, `meeting.started`, `meeting.completed` and `bot.failed`.
- Signing: `X-Webhook-Signature: sha256=hex(HMAC_SHA256(secret, "<ts>." + rawBody))` plus `X-Webhook-Timestamp` (Unix seconds).
- `Authorization: Bearer <secret>` is also sent, for legacy compatibility only.
- `meeting.completed` carries `data.meeting.service_provenance {bot_admitted_at, bot_departed_at, bot_outcome: served|never_admitted|…, transcription_provider, lifecycle_contract_version}`.
- **The full envelope is not documented.**

**Behaviour.**
- The bot auto-leaves after 10 minutes without remote audio (`left_alone`).
- A host removal ends the session as `evicted`.
- There is a 4-hour hard cap on a session.
- Zoom meetings that block web clients fail with `zoom_requires_rtms`.

**Not available in 0.12.**
- Live updates use **polling**: there is no WebSocket. `/agent/meeting/stream` is an agent feature and is not used.
- `PUT …/config` returns 404.
- **Bot chat is contradictory.** The docs say `POST …/chat` returns 404, but the v0.12.25 notes mention `…/acts` with a chat alias. **The consent chat message is therefore best-effort and capability-probed.**

**Deployment.** Upstream runs its own compose stack (`make all`), with its own Postgres and Valkey.
- Services: gateway (:18056), admin-api, meeting-api, runtime, agent-api, terminal and storage.
- **The bot image is built locally (`make bot`).** The `vexaai/vexa-bot:dev` image on Docker Hub is the incompatible 0.10 line.
- The runtime spawns one browser container per meeting through the Docker socket.

**Must be verified against the v0.12.28 checkout during C1**, and recorded in `deploy/vexa/VERIFIED.md`:
- the internal gateway port and service names;
- the S3 bucket environment variable names;
- the shape of the POST /bots response;
- the webhook envelope;
- whether the gateway accepts a private webhook URL;
- the chat endpoint;
- how API tokens are minted.

**Fallback if Vexa fails** (bot screening, stability or licence): fork ScreenApp `meeting-bot` (MIT). Only `lib/bot/vexa/**` would be replaced, because everything else talks to the `BotProvider` interface (see A1).

## Findings in the current code that shape the design
1. **A long ASR job would delay a bot join.** The single `meetsum` BullMQ worker runs at `MEETSUM_WORKER_CONCURRENCY=1` with a 30-minute lock (`processor.ts:1231-1243`), so a long ASR job would hold a delayed join past the meeting start. Bot jobs therefore run on a **separate queue `meetsum-bot`** with its own Worker in the same process (`worker/index.ts`). They write no `jobs` rows: `bot_sessions` is the record, so a dispatch delayed by hours doesn't sit in the job center as "queued". `lib/jobs/queue.ts` stays untouched, which avoids conflicts with M4 and M6. Finalize hands over to the normal `enqueueMeetSumJob("media.ingest")`, which does show in the job center.
2. **Calendar coverage.**
   - `pollCalendar` (`services.ts:1246`) runs every 15 minutes, only over the workspace DWD subject's calendars.
   - It stores `calendar_events.raw`, the full event, so rules can be re-evaluated without calling Google.
   - It upserts the `meetings` row (`id = createHashedId("meet_google", calendarEventId)`, status `scheduled`).
   - `extractMeetLink` only knows Meet (`hangoutLink ?? entryPoints[0]`).
   - `shouldImportCalendarEvent` drops events that have only a Zoom or Teams link and no attendees.
   - A cancelled event sets the meeting to `failed`.
   - Calendar scopes are read-only, so auto-inviting the bot account needs `calendar.events` added to DWD (opt-in).
   - The incremental path (`syncToken` with `singleEvents` unset) can return recurring masters. We only schedule for events that have `start.dateTime` and no `recurrence` array; instances carry `recurringEventId`.
3. **Status and storage hooks that already exist.**
   - `MeetingSource` already includes `meeting_bot`.
   - `MeetingStatus` has no "recording" value, and **we do not add one**: live state is derived from `bot_sessions`.
   - `importPlatformRecording` (`recording-import.ts`) is the pattern to follow for streaming into storage with `findMediaAssetBySourceFile` idempotency and `classifyRecordingImportError`.
   - Reuse `storeMeetingObjectStream` and `getUploadLimits().maxRecordingBytes`.
4. **SSRF.** `url-guard` blocks private IPs, but Vexa is internal (`http://vexa-gateway:…`). The Vexa client therefore does not go through `guardedWebhookFetch`. Instead:
   - the base URL comes only from env and is validated at boot;
   - paths are built from validated enums and regexes;
   - fetch uses `redirect:"error"`;
   - user-supplied URLs are never fetched. They are parsed, and only canonical URLs rebuilt from allowlisted hosts are passed as data.
5. **Security plumbing to reuse.**
   - `rate-limit.ts` is in-memory per process, so the Join-now cap is also enforced in the DB.
   - `secret-crypto.ts` `encryptSecret` is used for passcodes.
   - The `zoom` route is the pattern for public webhooks (`withPublicRoute`, raw body, 401 on a bad signature).
6. **UI building blocks.**
   - `StatusPill` supports `live|processing|new|review|failed`.
   - `LiveDot` and the `--live` token exist.
   - The z-index layer for the dock is `--z-dock: 15`.
   - The showcase defines the bot steps: Scheduled → Joining → Waiting to be admitted → Recording → Processing, plus Blocked with a reason and a fallback (`design-system/showcase/cadence.js:1214`).
   - The recorder dock CSS is in `cadence.css:491`.
   - `operational-pages.tsx:2284` still says the meeting bot is "deferred"; remove that text.
7. **VPS capacity.** The VPS has about 7.6 GB of shared RAM, and each bot needs about 1 vCPU and 1 GB. The default is therefore `MEETSUM_BOT_MAX_CONCURRENT=2`.

## Model and rules (normative)
**Bot session.** One row per attempt to put a bot in one meeting. The status machine:
- Status ranks:
  - `scheduled` 0
  - `requested` 1
  - `joining` 2
  - `awaiting_admission` 3 and `needs_help` 3
  - `active` 4
  - `stopping` 5
  - terminal 6: `completed`, `failed`, `blocked`, `cancelled`
- A transition applies only if the new rank is higher than the old one. Lateral moves between `awaiting_admission` and `needs_help` are allowed. Terminal states are immutable.
- A late `joining` that arrives after `active` is recorded in `bot_events` with `applied=false`.

**Mapping Vexa statuses to ours.**
- These statuses map 1:1: `requested`, `joining`, `awaiting_admission`, `needs_help`, `active`, `stopping`.
- `completed` maps by outcome:
  - `bot_outcome = never_admitted`, or the bot never reached `active`: **blocked** with reason `not_admitted`.
  - `evicted` before `active`: blocked with `removed_by_host`.
  - `evicted` after `active`: `completed` with `removed_by_host`, and we still finalize.
  - Otherwise: `completed`.
- `failed` maps by reason:
  - `zoom_requires_rtms`: blocked with `platform_blocked`.
  - `auth_session_missing`: blocked with `bot_signed_out`.
  - Admission denied or timed out: blocked with `not_admitted`.
  - Anything else: `failed` with the reason redacted.
- `idle` and `scheduled` from Vexa are ignored.

**Status reasons** (an enum, localized in the UI):
- `user_stopped`, `user_opt_out`, `event_cancelled`, `event_moved`, `rule_disabled`, `missed_window`;
- `capacity`, `already_in_meeting`, `invalid_meeting_link`, `vexa_unavailable`, `vexa_misconfigured`;
- `not_admitted`, `removed_by_host`, `platform_blocked`, `bot_signed_out`, `left_alone`;
- `no_recording`, `stale`, `meeting_deleted`, `unknown`.

**Meeting status.**
- A bot session never sets a meeting to `failed`.
- Finalize moves `scheduled|created` → `media_found` when it stores the asset, and `media.ingest` takes over from there.
- A blocked or failed bot leaves the meeting unchanged. The UI shows the bot error and the fallback.

**Workspace isolation.**
- Every session has `workspace_id`.
- The webhook resolves the workspace **only** through the `bot_sessions` row: first by `vexa_meeting_id`, else by `(platform, native_meeting_id)` restricted to non-terminal sessions, newest first.
- Routes check the meeting with `ctx.meetings.getMeeting(id)` and return 404 when it isn't visible.
- One live bot is allowed per `(platform, native_meeting_id)` across the instance, enforced by a partial unique index. A second workspace gets 409 `bot_already_in_meeting` without any detail about the other workspace.

**Origins.**
- `manual`: Join now with a URL.
- `meeting_request`: "Send bot" on an existing meeting.
- `calendar_rule`: auto-join.

Only `calendar_rule` sessions are cancelled when rules change. A user opt-out on a calendar event stores `cancelled/user_opt_out` and is **never** recreated by later polls, because the unique key `(workspace_id, calendar_event_id)` already exists.

**Auto-join rules** (`bot_rules` in `workspace_settings`, key `botRules`).
- `autoJoin` takes one of these values:
  - `off` (the default).
  - `all`.
  - `external_only`: at least one non-declined attendee has a domain outside the internal domains. Internal domains are the domains of workspace members' emails plus `MEETSUM_BOT_INTERNAL_DOMAINS`.
  - `owner_only`: the event organizer is a workspace member.
- Other fields:
  - `joinLeadSeconds`: 0–600, default 60.
  - `botName`: 1–60 characters, default `MEETSUM_BOT_NAME`.
  - `consentEnabled`: default true.
  - `consentMessage {he, en}`.
  - `languageMode`: `meeting|he|en|auto`.
  - `minAttendees`: default 2.
  - `skipTitlePatterns[]`.
  - `consentAcknowledgedAt` and `consentAcknowledgedByUserId`.
- **Auto-join cannot be turned on until an admin acknowledges the recording-consent notice** (PUT returns 400 `consent_ack_required`).

**Events that are always skipped:**
- events with no supported link;
- all-day events;
- events where the subject declined (`self.responseStatus=declined`);
- events whose start is more than `MEETSUM_BOT_LATE_JOIN_MAX_MINUTES` in the past;
- platforms not listed in `MEETSUM_BOT_PLATFORMS`;
- events whose title matches the skip patterns.

**Consent.**
- On the transition to `active`, a `bot.consent` job sends the localized message. The language is the meeting language (he → the `he` text).
- The `{owner}` placeholder is the requester's name, or the workspace name.
- If the chat endpoint returns 404 or 405, `consent_status` is set to `unsupported` and the UI tells the host to announce the recording.
- **The bot name must always signal recording.** The default is `MeetSum Notetaker`, and the settings UI previews it with "· מקליט" or "· Recording".
- **Legal note** (in the runbook and the settings panel; this is not legal advice):
  - Under Israel's Secret Monitoring Law (1979), a recording made by a participant is not covert monitoring.
  - Under the Privacy Protection Law, Amendment 13 (in force since August 2025), notice and transparency are expected.
  - MeetSum announces the recording through the bot name and the chat message, and requires the admin acknowledgment above.
  - Recordings follow the workspace retention settings.

**Google Meet bot screening:**
- Use a dedicated Workspace bot account (`MEETSUM_BOT_ACCOUNT_EMAIL`, for example `notetaker@realization.co.il`), with the bot browser profile signed in (`authenticated:true`). Same-domain meetings then usually admit the bot without a knock.
- Optionally invite the bot account to the event through the Calendar API (`MEETSUM_BOT_CALENDAR_INVITE=true`, which needs the `calendar.events` DWD scope).
- The UI shows an "admit MeetSum Notetaker" state.
- If the bot waits longer than `MEETSUM_BOT_AWAITING_ADMISSION_TIMEOUT_MINUTES`, reconcile stops it and marks it `blocked/not_admitted`.
- The bot account is excluded from calendar participants and from speaker candidates.

Implementation rules:
- **Options and request construction.**
  - Options are `{baseUrl, apiKey, fetch?, timeoutMs=VEXA_TIMEOUT_MS, streamTimeoutMs, retries=2, now?, sleep?}`.
  - Every request sends `X-API-Key` and uses `redirect:"error"` and `AbortSignal.timeout`.
  - Path segments go through `encodeURIComponent` after validation: `platform` must be in the enum and `nativeId` must match `^[A-Za-z0-9:._@%-]{3,300}$`.
- **Retries.**
  - GET and DELETE retry on 429, 5xx and network errors with exponential backoff plus jitter (500 ms base). `Retry-After` is honoured.
  - **POST /bots is never auto-retried.** BullMQ retries it, guarded by `findActiveBot`.
- **Errors.** `VexaError {kind: config|auth|conflict|capacity|invalid|not_found|unavailable|timeout|network|bad_response, status?, code?, retryable}`:
  - 401 → `auth`
  - 403 with a concurrency body, or 429 → `capacity`
  - 409 → `conflict`
  - 422 → `invalid`
  - 404 → `not_found`
  - 503 → `unavailable`, or `config` when the body mentions `TRANSCRIPTION_SERVICE`
- **Redaction:** messages never contain the API key, a passcode, `pwd=`, `p=`, `passcode`, or `Authorization`. Bodies are truncated to 300 characters.
- **Parsing:** zod schemas with `.passthrough()` for the undocumented shapes. `vexaMeetingId` is read from `id | meeting_id | meeting.id`.
- **Base URL check:** `raw_url` is followed only when its origin equals the base URL's origin. Otherwise the client builds `/recordings/{rid}/media/{mid}/raw` itself.

**A2. `parseMeetingLink(input)` and `extractMeetingLinks(text)`.** These are pure and never fetch.

Normalization before matching:
- HTML-decode (`&amp;`, `&#x2F;`).
- Strip `<a href>` down to the href.
- Remove bidi controls: U+200E, U+200F, U+202A–U+202E, U+2066–U+2069, U+061C.
- Map fullwidth characters with NFKC.
- URL tokens are ASCII-only (`[A-Za-z0-9\-._~:/?#\[\]@!$&'()*+,;=%]`). A run therefore stops at the first Hebrew letter, space, `״` or `׳`.
- Trailing `.,;:!?)]}>"'` and Hebrew punctuation are trimmed. Balanced parentheses are kept.
- Known wrappers are unwrapped without fetching:
  - `google.com/url?q=`
  - `*.safelinks.protection.outlook.com/?url=`
  - `urldefense.com/v3/__…__`

Platform rules:
- **Meet.** `meet.google.com/<abc-defg-hij>` (case-insensitive, lowercased). Query strings (`authuser`, `hs`, `pli`) are ignored. `meet.google.com/lookup/*` and `tel:` are unsupported.
- **Zoom.**
  - `(*.)zoom.us|zoom.com|zoomgov.com` with `/j/<9–11 digits>`, `/w/<id>`, `/s/<id>` or `/wc/join/<id>`.
  - The passcode is read from `pwd=`.
  - `/my/<vanity>` is unsupported (`personal_link`).
- **Teams.**
  - `teams.microsoft.com/l/meetup-join/<19:meeting_…@thread.v2>/…?context=` gives the native ID as the decoded thread. `canonicalUrl` keeps `context`, which carries the tenant and organizer.
  - `teams.microsoft.com/meet/<10–15 digits>?p=` and `teams.live.com/meet/<digits>?p=` give the numeric ID and the passcode. `teamsBaseHost` is set for `teams.live.com`, GCC and DoD hosts (`gov.teams.microsoft.us`, `dod.teams.microsoft.us`).
- Rejected: any other host, `http:` downgrades (normalized to https), credentials in the URL, and inputs longer than 4 KB.
- **Results.** `extractMeetingLinks` returns the matches in order, de-duplicated by `(platform, nativeId)`. `redactedUrl` drops the `pwd`/`p` values and the Teams `context` query.

**A3. Picking the link for a calendar event** (`extractCalendarMeetingLink(event)`). Priority order:
1. `conferenceData.entryPoints` with `entryPointType:"video"`;
2. `hangoutLink`;
3. `location`;
4. `description`.

The first supported link wins. The `source` field records where it came from.

**A4. Rules** (`evaluateAutoJoin({rules, event, link, members, internalDomains, subject, now, config}) → {join: true, dispatchAt} | {join: false, reason}`).
- This is pure and implements every rule in the Model section.
- `dispatchAt = max(now, start − lead)`.
- An event is in the window if `now ≤ (end ?? start + MEETSUM_BOT_LATE_JOIN_MAX_MINUTES)`.

`lib/settings/bot-rules.ts` provides `getBotRules(wsId)` and `updateBotRules(wsId, patch, actor)`:
- Values are validated and clamped.
- Consent messages are 1–500 characters and must not contain URLs.
- Turning on auto-join requires `consentAcknowledgedAt`. Sending `acknowledgeConsent:true` stamps the time and the actor.
- Storage follows the same memory/postgres pattern as `app-settings.ts`.

**A5. Calendar sync** (`lib/bot/calendar-sync.ts`).
- **`syncCalendarBotSession`:**
  - Load the existing session by `(ws, calendarEventId)`.
    - If it is `cancelled/user_opt_out` or `origin≠calendar_rule`, update only `scheduled_start`/`scheduled_end` and return.
  - Evaluate the rules.
    - No join and the session is `scheduled` → `cancelled/rule_disabled`.
    - Join and no session → create one: origin `calendar_rule`, the `meeting_id` from the poll, `passcode_enc`, and `bot_name`/`language` from the rules and the meeting. Then call `scheduleDispatch`.
    - Join and a session exists:
      - status `scheduled` and the start changed → `dispatch_rev++`, new `dispatch_at`, `removeBotJob(oldId)`, then `scheduleDispatch`;
      - live → no change.
  - Optionally invite the bot account (`events.patch` with `sendUpdates:"none"`, behind a flag, non-fatal).
- **`cancelCalendarBotSession`:** a `scheduled` session becomes `cancelled/event_cancelled`. A live session is left running.
- **`resyncWorkspaceBotSessions(wsId)`:** re-evaluates upcoming `calendar_events` (`raw`, joined to the workspace's identities) for the next `lookahead` window. It is used after a rules change.

**A6. Dispatcher** (`lib/bot/dispatch.ts`).
- **`scheduleDispatch(session)`:** `enqueueBotJob("bot.dispatch", {sessionId, rev, workspaceId}, {jobId:"bot.dispatch:<id>:<rev>", delay: max(0, dispatch_at−now)})`.
- **`runDispatch({sessionId, rev})`:**
  1. Lock the row. Skip unless `status='scheduled'` and the rev matches.
  2. Window passed → `cancelled/missed_window`. Only `calendar_rule` sessions use the calendar late-join window; a manual or meeting_request session's window runs `MEETSUM_BOT_LATE_JOIN_MAX_MINUTES` from the later of the meeting start and the request (`requested_at`, else `created_at`).
  3. Instance or workspace capacity reached → re-delay 60 s through `rev++`, as long as the window allows it; otherwise `failed/capacity`.
  4. Mark `requested` (`attempts++`, `requested_at`). A unique-index violation → `blocked/already_in_meeting`.
  5. Commit, then call `requestBot` with `{transcribe_enabled: config.transcribe || liveFlag, recording_enabled:true, authenticated: config.authenticated, automatic_leave:{max_time_left_alone: MEETSUM_BOT_LEFT_ALONE_MS}, language}`. Teams and Zoom also get `meeting_url: canonicalUrl` and the decrypted passcode.
  6. Handle the result:
     - success → store `vexa_meeting_id`;
     - `conflict` → `findActiveBot`; if the bot is ours, adopt it; otherwise `blocked/already_in_meeting`;
     - `capacity` → revert to `scheduled` and re-delay;
     - `invalid` → `failed/invalid_meeting_link` (an `UnrecoverableError`);
     - `config`/`auth` → `failed/vexa_misconfigured`;
     - retryable → rethrow; BullMQ retries 4 times with a 15 s backoff, and each retry first calls `findActiveBot` to adopt a bot that may already exist.
  7. After a successful POST or adoption, re-read the session: if a user stop or a cancel landed meanwhile (`stopping` or terminal), call `stopBot(platform, native id)` and return `stopped` instead of `requested`. A retry job for a `stopping` session stops any bot of ours for the target and ends a session without a Vexa id as `cancelled/user_stopped`. The service's stop on a `requested` session without a Vexa id only marks it `stopping`; reconcile cancels one that stays like that for 10 minutes.
- **`dispatchNow(sessionId)`:** used by Join now and Send bot.

**A7. Bot queue and worker.**
- `meetsum-bot` queue on `REDIS_URL`.
- Worker concurrency `MEETSUM_BOT_WORKER_CONCURRENCY` (4), lock 30 minutes for finalize.
- Job routing:
  - `bot.dispatch` → A6
  - `bot.consent` → A8
  - `bot.finalize` → B `finalizeBotSession` (attempts `MEETSUM_BOT_FINALIZE_ATTEMPTS` = 8, exponential backoff from 30 s)
  - `bot.reconcile` → A9
  - `bot.retention` → B
- **Schedulers** (BullMQ `upsertJobScheduler`, so multiple worker processes don't duplicate them): reconcile every `MEETSUM_BOT_RECONCILE_SECONDS` (120); retention daily.
- A job whose `workspaceId` has been deleted → `UnrecoverableError`.

**A8. Consent.**
- Skip if `consentEnabled=false` (`consent_status=disabled`) or the status is not yet `sent`.
- Call `sendChat`. Set `consent_status` from the result (`sent`/`unsupported`/`failed`, with 2 retries).

**A9. Reconcile** (the polling fallback when a webhook is missed). Every tick:
- (a) `listDueForDispatch`: sessions with `scheduled` and `dispatch_at ≤ now` that have no delayed job (`queue.getJob` is null) → `dispatchNow`.
- (b) Open sessions with `last_event_at` older than `MEETSUM_BOT_STALE_MINUTES` → `getMeeting(vexa_meeting_id)` → B `applyVexaSnapshot` (`source:"poll"`).
  - 404 → `failed/stale`.
  - `requested` for more than 10 minutes with no `vexa_meeting_id` → `failed/vexa_unavailable`.
- (c) `awaiting_admission` or `needs_help` for longer than the timeout, measured from `status_changed_at` (set only when a status change applies, so stale polls never reset it) → `stopBot` → `blocked/not_admitted`.
- (d) Live sessions whose `meeting_id` is null (the meeting was deleted) → `stopBot`, reason `meeting_deleted`.
- (e) `completed` sessions with `recording_status='none'` and recording enabled → enqueue finalize.
- (f) The payload `{workspaceId, resyncRules:true}` → `resyncWorkspaceBotSessions`.

**B1. Postgres store.**
- Every statement is scoped by `workspace_id`, except `findByVexaMeetingId` and `findOpenByTarget`, which are webhook-only and return the session's own workspace.
- `transition` runs in one transaction: `select … for update`, a rank check, `update`, and an `insert` into `bot_events`.
- `last_event_at` is bumped by every applied transition and by unapplied webhook/API events, but not by an unapplied poll. `status_changed_at` is set only when the status actually changes.
- `joined_at` is set on the first `active`, and `left_at` on a terminal status.

**B2. Lifecycle** (`lib/bot/lifecycle.ts`, pure).
- `mapVexaStatus(vexaStatus, {reason, provenance, wasActive}) → {status, reason} | undefined` implements the Model table. `wasActive` is `joined_at` (the first applied `active`) or `provenance.bot_admitted_at`; `stopping` alone does not count, so a user stop before admission ends `cancelled/user_stopped` without finalize.
- `applyBotStatus(session, next)` returns `{patch, sideEffects:("enqueue_finalize"|"enqueue_consent"|"notify")[]}`:
  - `active` → consent;
  - `completed` with recording enabled and the bot reached `active` → finalize;
  - `blocked`/`failed` → no finalize.
- `applyVexaSnapshot(store, session, vexaMeeting, source)` is shared by the webhook and reconcile.

**B3. Webhook.** `POST /api/integrations/vexa/webhook` is wrapped in `withPublicRoute("Vexa webhook: HMAC-SHA256 signed with VEXA_WEBHOOK_SECRET")` and runs with `runtime="nodejs"`. Steps:
1. The bot feature is disabled or the secret is missing → 503.
2. The raw body is larger than 256 KB → 413.
3. `verifyVexaSignature(headers, raw, secret, now)`:
   - `X-Webhook-Timestamp` must be within `VEXA_WEBHOOK_TOLERANCE_SECONDS` (300).
   - The expected value is `sha256=` + the HMAC of `ts + "." + raw`.
   - The comparison is `timingSafeEqual` on equal-length buffers.
   - A Bearer token is accepted only when `VEXA_WEBHOOK_ALLOW_BEARER=true`, also compared in constant time.
   - Failure → 401 with no detail.
4. Parse the body tolerantly: `event_type|event|type`, `event_id|id`, `data.meeting{id, platform, native_meeting_id, status, data?}` or top-level `meeting_id` / `status` / `reason`.
5. Resolve the session (see the Model section). If none is found, record nothing and return 200 `{ignored:true}`.
6. `recordEvent` (deduplicated). A duplicate → 200 `{duplicate:true}`.
7. `mapVexaStatus` → `transition` → side effects: `enqueueBotJob("bot.finalize", …, {jobId:"bot.finalize:<id>"})` and consent.
8. Return 200 within about 100 ms. No Vexa call happens inside the request.
9. The stored payload is redacted: URL queries and any `*secret*`/`*token*` keys are stripped.

`meeting.completed` provenance is copied into `bot_events.payload`. `bot.failed` is treated as `failed` with its reason.

**B4. Finalize** (`finalizeBotSession({sessionId, workspaceId, provider?, storage?})`). Idempotent:
1. Skip if `recording_status='imported'` and `ingest_job_id` is set.
2. Skip if the meeting was deleted (`no_recording`).
3. `getMeeting(vexa_meeting_id)` → the audio recording (`recordings[]`, else `getRecordingMaster`).
   - No recording yet → set `recording_status='pending'` and throw a retryable error.
   - Still missing after the final attempt → `recording_status='missing'`, reason `no_recording`.
4. `findMediaAssetBySourceFile("meeting_bot", "vexa:<rid>:<mid>", {meetingId})` → reuse the asset if it exists.
5. Otherwise `streamRecordingMedia` → sniff with `assertSupportedMedia` → `storeMeetingObjectStream({keyPrefix:"meetings/<meetingId>", filename:"bot-<sessionId>.<ext>", maxBytes: maxRecordingBytes})` → `createMediaAsset({kind:"original", source:"meeting_bot", sourceFileId, retention:"audio", metadata:{vexaMeetingId, platform, botSessionId}})`.
   - On error, delete the stored object. Errors are classified like `classifyRecordingImportError`.
6. Meeting `scheduled|created` → `media_found`.
7. If `transcribe_enabled`, `getTranscript` → `speaker_timeline`. This step is non-fatal.
8. `enqueueMeetSumJob("media.ingest", {meetingId, workspaceId, assetId, source:"meeting_bot"})`, then store `ingest_job_id` and `recording_status='imported'`.
   - The check-and-set happens in one transaction (`for update`), so duplicate webhooks or reconcile runs enqueue at most once.
   - Our ASR router then produces the final Hebrew transcript, and M4's `media.prepare` follows automatically.

**B5. Speaker timeline.**
- Vexa segments are grouped into runs of `{name, startMs, endMs}`. Gaps of 1.5 s or less are merged.
- Empty speakers and the bot's own name or email are dropped.
- **Offset:** use `absolute_start_time` minus the recording start when both are known. Otherwise use offset 0, but only when the recording duration is within 2% of the session span; if not, return `undefined`.
- `loadBotSpeakerTimeline` returns the timeline from `bot_sessions`. It feeds the existing M3 `meet_alignment` signal, with the detail `"bot"`.

**B6. Retention** (daily).
- Applies to sessions where either:
  - `recording_status='imported'` and `updated_at < now − MEETSUM_VEXA_ARTIFACT_RETENTION_HOURS` (72); or
  - the session is terminal with no recording and is older than the same cutoff.
- For each one, call `deleteMeeting(vexa_meeting_id)`. 204/200/404 → set `vexa_purged_at`. 409 → skip.
- Prune `bot_events.payload` to `{}` after 30 days.

**B7. Service and routes.** All responses use `BotSessionSummary` and never include passcodes or raw URLs. Every action is audited.
- **`POST /api/meetings/bot`** (`meeting:create`). Body: `{meetingUrl|text, title?, language?: "he"|"en"|"auto"}`.
  - Rate limits:
    - in memory: `{maxRequests:5, windowMs:60_000}`, keyed by `user:<id>`;
    - in the DB: `countCreatedSince(ws, 1h)` must not exceed `MEETSUM_BOT_JOIN_RATE_PER_HOUR` (20), else 429 `bot_rate_limited`.
  - Capacity check → 429 `bot_capacity`.
  - Parse with `extractMeetingLinks`. Nothing found → 400 `invalid_meeting_link {reason}`.
  - The workspace already has an open session for the same target → 200 with that session (`reused:true`).
  - Otherwise, attach to an existing meeting when a visible `scheduled` meeting's `google_meet_link` or calendar link matches and it starts within ±2 hours. If not, `ctx.meetings.createMeeting({source:"meeting_bot", title: title ?? "<Platform> meeting", language, ownerUserId})`.
  - Create the session (`origin:"manual"`) → `dispatchNow` → 201 `{meeting, session}`.
  - A unique-index race → 409 `bot_already_in_meeting`.
- **`GET /api/meetings/[id]/bot`** (`meeting:read`) → `{session?: BotSessionSummary, history: BotSessionSummary[], canSend, link?: {platform, redactedUrl}}`.
- **`POST /api/meetings/[id]/bot`** (`meeting:write`), "Send bot to this meeting":
  - The link comes from the body, else calendar `raw`, else `google_meet_link`.
  - The start is beyond the lead time → `scheduled` with `dispatch_at`. Otherwise → dispatch now.
  - An existing calendar session in `cancelled/user_opt_out` is reopened: `scheduled`, `rev++`.
- **`DELETE /api/meetings/[id]/bot`** (`meeting:write`):
  - `scheduled` → `cancelled/user_opt_out`, and the job is removed.
  - Live → `stopBot` → `stopping/user_stopped`.
  - Terminal → 409.
- **`GET /api/bot/sessions?active=1`** (`meeting:read`) → open sessions plus terminal sessions from the last 24 hours, for meetings the caller can see (join with `meetingScopeSql`). The result is keyed by `meetingId`, so the inbox needs no change to the repository list SQL.
- **`GET /api/bot/status`** (`ops:read`) → `{enabled, vexaVersion, healthy, running, capacity:{max, perWorkspace}, webhookConfigured}`.
- **`GET /api/settings/bot`** (`workspace:read`) and **`PUT /api/settings/bot`** (`settings:write`):
  - Validation errors → 400 with per-field errors.
  - A successful PUT enqueues `bot.reconcile {workspaceId, resyncRules:true}` and audits `bot.rules.updated` (plus `bot.consent.acknowledged`).

**B8. Live transcript** (stretch, only when `MEETSUM_LIVE_TRANSCRIPT=true` and the session has `transcribe_enabled`).
- Route: `GET /api/meetings/[id]/bot/live` (`meeting:read`). It returns `text/event-stream` with `cache-control: no-cache, no-transform` and `x-accel-buffering: no`, and runs with `runtime="nodejs"` and `dynamic="force-dynamic"`.
- One shared in-process poller per session calls `getTranscript` every `MEETSUM_LIVE_POLL_MS` (2000).
- Events:
  - `segment {id, speaker, text, startMs, endMs, language, final}` is an upsert keyed by `segment_id`;
  - `status`;
  - `end`, sent when the session is terminal.
- A keep-alive comment is sent every 15 s.
- The stream closes on client abort, and the poller stops when it has no subscribers.
- At most `MEETSUM_LIVE_MAX_STREAMS` streams per process; beyond that → 429.
- The flag is off, or transcription is disabled → 404 `live_unavailable`.

**C1. Infrastructure.**
- **Decision:** Vexa runs as its **own compose project** (`-p vexa`) from the upstream checkout at **`v0.12.28`**, pinned by commit SHA. We do not re-declare upstream services in our files, for two reasons:
  - the bot image has to be built locally from the same tag;
  - re-declared services drift every release.
- **Our pinned files:**
  - `deploy/vexa/vexa.lock`: repo, tag, SHA, and the resolved image digests written by `bootstrap.sh`.
  - `deploy/vexa/compose.override.yml`. It does the following:
    - binds every upstream port to `127.0.0.1` or removes it;
    - adds the external network `meetsum-vexa` to the gateway and the meeting-api;
    - sets `RECORDING_ENABLED=true` and `TRANSCRIBE_ENABLED=false`;
    - sets the gateway `GUARD_TRUSTED_PROXIES`;
    - sets `MINIO_ENDPOINT=meetsum-minio:9000` and `MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` to dedicated Vexa credentials, with the bucket from `VEXA_MINIO_BUCKET=vexa-recordings`. The exact bucket variable is confirmed during verification; if the MinIO wiring can't be confirmed, keep upstream versitygw. **Finalize reads recordings through the Vexa API, so the storage backend doesn't affect behaviour.**
    - sets `mem_limit` and `cpus` per service.
  - `deploy/vexa/vexa.env.example`: `ADMIN_TOKEN`, `INTERNAL_API_SECRET` (must be real; 0.12.27 refuses to boot on placeholders), the MinIO credentials, and `BROWSER_IMAGE=vexa/vexa-bot:<sha>`.
  - `deploy/vexa/bootstrap.sh`, which runs these steps:
    1. clone or fetch the repo;
    2. check out the SHA and verify it matches the tag;
    3. `make bot`, tagged with the SHA;
    4. pull the images;
    5. record the digests;
    6. `docker compose -p vexa -f deploy/compose/docker-compose.yml -f <override> up -d`;
    7. wait for gateway health.
  - `deploy/vexa/VERIFIED.md`: the items from the verification list, checked against the tag.
- **`docker-compose.vexa.yml`** (a new file, **profile `vexa`**, used with `-f docker-compose.prod.yml -f docker-compose.vexa.yml --profile vexa`):
  - a one-shot `vexa-minio-init` service (`minio/mc:<pinned tag+digest>`) creates the bucket, the user and a bucket-only policy, plus a lifecycle rule that expires objects after 7 days as a safety net;
  - it attaches `app` and `worker` to the external network `meetsum-vexa`;
  - it sets no `:latest` tags.
  - Existing compose files are not edited, which avoids conflicts with M6's Postgres image change.
- **Security.**
  - The runtime needs `/var/run/docker.sock`, which is root-equivalent. The runbook therefore recommends running it through `tecnativa/docker-socket-proxy` (pinned) with only the containers, images and networks APIs enabled. If that is incompatible with the upstream runtime, document the risk and isolate the host.
  - Vexa APIs are never exposed through Traefik.
- **`scripts/vexa-configure.ts`.** It calls `health`, then `configureWebhook({url: VEXA_WEBHOOK_URL ?? NEXT_PUBLIC_APP_URL + "/api/integrations/vexa/webhook", secret: VEXA_WEBHOOK_SECRET, events: {"meeting.status_change":true, "meeting.completed":true, "bot.failed":true, "meeting.started":true}})`, then `getWebhook`, and prints the masked result. If the gateway rejects the internal URL, use the public `https://meetsum…/api/integrations/vexa/webhook`.
- **vexa-compose test** (parses the YAML):
  - no `:latest`;

  - every service carries the `vexa` profile;
  - no ports are published on 0.0.0.0;

## Acceptance criteria
1. **Migration and gate.** 024 applies on M6 data and re-runs idempotently. With `MEETSUM_BOT_ENABLED=false`, behaviour is identical to M6 (calendar, worker and UI unchanged).
2. **Join now.**
   - Pasting Hebrew invite text that contains a Meet, Zoom (with `pwd`) or Teams link creates a meeting and a session.
   - The Vexa POST body matches the fixture.
   - Signed webhooks requested → joining → awaiting_admission → active → completed move the UI from Joining to Waiting (with the admit hint) to Recording (dock and live pill).
   - Finalize stores exactly **one** `media_assets` row (`kind original`, `source meeting_bot`) and enqueues **one** `media.ingest`, even with duplicate or out-of-order webhooks plus a concurrent reconcile run.
   - Our ASR router then produces the transcript, and the bot timeline feeds speaker suggestions.
3. **Calendar.**
   - An event with an external attendee and a Teams link in a Hebrew description, under rule `external_only` with lead 60, gets `dispatch_at = start−60s`, and the dispatch fires at that time (fake timers).
   - Moving the event reschedules it, and the old job is a no-op.
   - Deleting the event cancels it.
   - Turning auto-join off cancels future `calendar_rule` sessions only.
   - A user's "Don't send bot" survives later polls.
   - An event created 5 minutes before start still dispatches through the poll or reconcile path.
4. **Failure paths.**
   - Never admitted → blocked/not_admitted, with no finalize, and the fallback recorder is offered.
   - `auth_session_missing` → "Bot signed out".
   - 403 capacity → re-delay.
   - 409 by another workspace → blocked with no detail leaked.
   - A missed webhook is recovered by reconcile within 2 polling intervals.
5. **Security.**
   - A bad, stale or replayed signature → 401, or a 200 no-op for a replay.
   - Passcodes are encrypted at rest and absent from logs, responses and `bot_events`.
   - Join now is rate-limited (429).
   - Vexa is reachable only via `VEXA_API_URL`, and its ports are not public.
   - Auto-join requires the admin consent acknowledgment.
   - The consent message is sent, or flagged as unsupported with a UI prompt.
6. **UI.** he and en, light and dark. Pills appear only for exceptions; `--live` is used only for active recordings and the dock. Timers are LTR-isolated, and names are wrapped in `<bdi>`.
7. **Infrastructure.** `vexa.lock` is pinned to v0.12.28 with its SHA and digests, and the compose test passes. The runbook covers the bot account, Workspace admin allow-listing, capacity, upgrades and the legal note.
8. **Green checks:** `npm run typecheck && npm run lint && npm test && npm run build`. Manually: `npm run bot:simulate --fake-vexa` takes a meeting through to a transcript, and one real Meet join is tested in staging once the bot account exists.

## Risks and decisions
- **Undocumented Vexa shapes.** The POST /bots response, the webhook envelope and the recordings list are not documented. Parsing is tolerant, the fixtures are marked `_synthetic`, and C1 re-records them from v0.12.28 (`scripts/bot-simulate.ts --record` against a real gateway). Bot chat may be unavailable, so the consent fallback is mandatory.
- **No live WebSocket in 0.12.** The live view is therefore poll-based SSE, behind a flag. It also requires a Vexa STT backend: either a hosted token, which sends audio to a third party and must be decided by the owner, or a GPU unit. Hebrew quality of that draft is unknown. The final transcript always comes from our router.
- **Calendar coverage.** Only the workspace DWD subject's calendars are covered. Outlook arrives in M8.
- **Docker socket exposure.** The runtime needs the Docker socket; mitigate with a socket proxy or a dedicated host.
- **External Meet screening.** It can still block the bot in meetings outside the Workspace. The fallback is the browser or desktop recorder, offered in the UI.
- **Deferred to M8:** customer-facing webhook events for bot status (keep the catalog consistent).
